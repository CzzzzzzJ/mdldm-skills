# 实际实现的读取链路

1. discover 独立查找官方 Mac 容器；init 显式绑定源目录及范围。
2. capture 在微信运行时取得候选。内存扫描每轮最多 1 GiB 的可读写区并周期复扫；函数观察只捕获目标 salt 的相关候选。覆盖可能不全，doctor 明确显示缺失。
3. 每个候选均需通过目标库第一页 HMAC-SHA512 校验。密钥不打印、不写公共临时日志。
4. refresh 拒绝运行中的原微信；对选定源库及 WAL 计算哈希、复制、再次计算源签名并验证副本哈希。它是保守的离线快照实现，不声称提供活动数据库跨库事务一致性。
5. crypto 流式解密 4096 字节页，校验每页 HMAC，使用 AES-CBC，恢复 SQLite 头和保留字节。支持配置固定，不进行不安全的“失败后关闭校验”回退。
6. wal 检查头、页面大小、滚动校验和与日志世代，重放最后提交标记以内的帧，忽略未提交尾部；处理提交后的文件大小。WAL 页 1 的两种已知布局必须通过认证，不能只凭猜测选布局。
7. 私有明文副本将读写版本标记切为普通回滚模式，避免后续查询触发 live WAL；运行 SQLite integrity_check。
8. 所有选定数据库成功后才发布快照并原子切换 current。缺密钥、损坏页、WAL 校验失败、源变化均拒绝发布，保留上一份快照。
9. query 以 mode=ro&immutable=1 打开仅本包生成的快照，遍历 message_N，参数化筛选，按时间/分库/local_id 排序，跨库分页。

## 明确限制

- 当前是退出微信后的快照读取，不是无感实时同步。
- 非默认 SQLCipher 配置、回滚日志、未识别表结构会报错；不能为了“能打开”跳过认证。
- 文件哈希前后稳定并不等于对任意恶意/并发写入者的通用锁定保证。因此线上源必须先正常退出微信。
- 微信所有版本的字段、HMAC 设置及媒体布局不统一；真实兼容性仍需实机测试。
- 已选范围所有库解密成功，仅证明本地快照，不证明手机全量历史已同步。
